# window-organizer - smallest credible v1

Goal: a stranger downloads a `.dmg`, drags it to Applications, opens it, presses a
hotkey, and it works - without touching a terminal, editing JSON, or installing a
second daemon they've never heard of. That's the bar. Everything below either meets
that bar or explicitly gets cut.

## What v1 ships with

**Packaging (from GAPS.md section 1)**
- Single `.app` bundle wrapping the existing layout engine (`warrange`'s logic,
  ported into the app process rather than a separate CLI binary).
- Signed with a Developer ID, notarized, hardened runtime. Distributed as a `.dmg`
  outside the Mac App Store (see below for why the Store is out).
- A Homebrew cask pointing at the same signed build - cheap, and this audience will
  ask for it immediately.
- `wdump`/`wprobe` remain as internal debugging binaries (not user-facing), or get
  cut from the shipped bundle entirely and stay dev-only tools in the repo.

**Runtime shape (section 3)**
- One process: a menu-bar app (`NSStatusItem`). It owns the global hotkey itself
  (no skhd) and, when issue #2's recency recorder lands, runs that as an internal
  timer in the same process.
- Launch-at-login via `SMAppService`, toggleable from the menu.
- Menu bar icon visibly indicates: running normally / degraded (missing Screen
  Recording) / needs Accessibility.

**Permissions and onboarding (section 2)**
- First-run window: two sentences per permission, a button that deep-links to the
  exact System Settings pane, and live re-checking so the user never has to guess
  whether it "took."
- Because the app owns its own hotkey, there is only one process to grant
  Accessibility to - this alone removes the worst support-burden item in the spike
  (2.3, the skhd attribution problem).
- Runtime re-check before every arrange; a clear, specific error (not silence) if a
  permission was revoked after grant.

**Hotkeys (section 5)**
- In-process global hotkey registration. skhd dependency dropped entirely for the
  shipped app - it was a personal-spike convenience, not a product requirement.
- One default hotkey to start (arrange with master pane). Undo bound to a second
  default. Rebinding UI can wait (cut, see below) but the defaults must not collide
  with common system shortcuts.

**Configuration (section 4) - deliberately minimal**
- Ship with the existing category-default priorities baked in (`priority.swift`'s
  `defaultPriorities` table already covers the common app set well).
- A *minimal* preferences window: a list of currently-running apps with a tier
  picker (hero/normal/minor/banish) per app - not the full weight/maxSize/
  usefulSize editor. This solves "I don't want Slack taking half my screen" without
  building a general-purpose JSON editor with a GUI on top.
- Malformed-state handling: since v1's UI is the only writer of the config, this
  mostly self-solves, but keep the existing defaults-fallback behavior as a safety
  net and surface a visible error if the file is somehow corrupted (e.g. hand-edited
  by a power user).

**Runtime feedback (section 7)**
- Every state currently printed to a terminal (no windows, Mission Control open,
  cannot-fit windows, nothing to undo) gets a native notification or a menu-bar
  message instead. This is non-negotiable for v1 - an app that fails silently reads
  as broken, not calm.
- A visible "Undo last arrange" menu item in addition to its hotkey.
- Stow reasons (issue #2's "why was this window stowed") are IN SCOPE for v1's
  layout engine work regardless of this audit, since issue #2 is already spec'd and
  ready-for-agent - but the *UI* for showing those reasons (e.g., hovering a stowed
  app in a menu) can be as simple as a tooltip string, not a dedicated screen.

**Lifecycle (section 6)**
- Sparkle integration for updates. This is not optional even for v1 - shipping
  something with zero update path outside the App Store means the first
  Accessibility-API edge case that crashes it never gets fixed for anyone who hit it.
- A documented, findable "Quit and uninstall" menu action that removes the app,
  its LaunchAgent/login-item registration, and offers to delete `~/.window-spike/`
  (opt-in, not automatic - a user's tuned priorities are worth keeping across a
  reinstall).
- One-paragraph privacy statement shown at first run, before the Screen Recording
  prompt.

## Explicit cut list - what v1 does NOT include, and why

- **Mac App Store submission.** The Accessibility/window-manipulation surface this
  tool needs is very unlikely to clear Review. Don't spend v1 time on Store-specific
  sandboxing work; direct distribution is the only credible path (GAPS 1.4).
- **Full preferences UI (weight, maxSize, usefulSize per app).** The minimal
  tier-only picker above covers the 80% case (issue #2's own out-of-scope list
  already defers "any graphical preferences interface," so this is consistent with
  the team's own sequencing, just pulled slightly forward to tier-only). Full JSON-
  field editing stays a hand-edit for power users in v1.
- **Per-Space / per-display-arrangement profiles.** Real value, but it's a second
  layer on top of configuration that doesn't need to exist before the first one
  does. One display-count-aware default (more panes on a big external monitor) is
  the only concession worth making in v1, and even that can wait if it's not free.
- **Customizable hotkeys.** Ship with fixed, sensible defaults. Rebinding UI is a
  small but real chunk of work (key capture + conflict detection) that doesn't block
  anyone from using the app on day one.
- **Crash reporting.** Wire it up, but it is not a release blocker in the way
  signing/notarization/permissions are - it's an observability nice-to-have that can
  land in a fast-follow.
- **Import/export of config, profiles, localization, per-app compliance database.**
  All real, all deferred. None of them block a stranger's first successful arrange.
- **The Automator fallback documented in `setup-hotkey.sh`.** Drop it entirely once
  the app owns its own hotkey - it was only ever a workaround for the skhd
  dependency this v1 removes.
- **skhd itself.** Cut as a v1 dependency. It served the spike well (fast to stand
  up, zero GUI work) but every problem it causes (2.3's attribution confusion, a
  second unsigned daemon, a second Accessibility grant, Homebrew as a hard
  prerequisite) disappears once the app registers its own global hotkey. This is
  the single highest-leverage cut/build decision in the whole list.

## Honest sizing note

Sections 1-3 and 5 (packaging, permissions, runtime shape, hotkeys) are the real
work of turning a CLI spike into an app - they are not incremental polish on top of
the existing layout engine, they are a second, roughly-app-sized piece of
engineering (menu-bar shell, onboarding flow, in-process hotkey handling, sign/
notarize/update pipeline) wrapped around logic that already works. Budget
accordingly: the layout engine (the hard, interesting, already-mostly-solved part
per the README's measured results) is not the long pole for v1. The macOS app-shell
work is.
